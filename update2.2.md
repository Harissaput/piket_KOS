KosPiket — Prompt Fitur Login, Admin & ERD

Dokumen ini berisi: (1) keputusan desain, (2) ERD, (3) Prompt A untuk menambah fitur auth + dashboard admin, (4) Prompt B untuk memperbaiki masalah yang ditemukan. Salin tiap prompt ke AI coding agent Anda (Claude Code, Cursor, dsb.) secara berurutan: Prompt A dulu, baru Prompt B.

1. Keputusan desain

Pendaftaran mandiri: pengguna yang belum punya akun harus daftar dulu (email, password, nama, dan memilih slot anggota: Haris/Fahrul/Ishom yang belum diklaim).

Persetujuan admin: akun baru berstatus pending dan baru bisa masuk setelah admin menyetujui. Ini mencegah orang asing yang tahu URL ikut masuk dan mengklaim slot anggota. Kalau Anda ingin langsung aktif tanpa persetujuan, ubah satu baris di Prompt A (disebutkan di sana).

Peran: user dan admin. Admin tidak bisa dibuat lewat form daftar. Admin pertama dibuat manual lewat SQL, admin berikutnya lewat tombol "Jadikan admin" di dashboard admin.

Satu akun = satu anggota. Kolom profiles.member_id bersifat unik, sehingga satu slot anggota tidak bisa diklaim dua akun.

Keamanan di database, bukan hanya di UI. Semua pembatasan hak akses ditegakkan lewat RLS dan fungsi RPC SECURITY DEFINER, karena anon key terlihat di browser.

Kamu adalah senior engineer. Perbaiki daftar masalah berikut pada proyek KosPiket. Baca file terkait sebelum mengubah. Kerjakan satu per satu, jelaskan perubahan singkat per item, dan pastikan `npm run build` serta `npm run lint` lolos. Jangan mengubah desain visual selain yang diminta.1. Form tukar jadwal, konfirmasi piket, dan izin harus memakai member milik user yang login (useAuth). Hapus nilai default hardcoded seperti 'm1', 'm2', '2026-09-07', '2026-09-08'.3. TUKAR JADWAL TIDAK ATOMIK. approveSwapRequest di swap.service.ts melakukan beberapa query terpisah dan menelan error. Ganti dengan pemanggilan RPC respond_swap_request (transaksi tunggal), tampilkan error ke UI, dan tambahkan validasi: tanggal tidak boleh di masa lalu, tidak boleh jatuh di hari libur, dan kedua tanggal memang jadwal pihak masing-masing.4. FALLBACK YANG MENUTUPI ERROR. Hapus fallback data palsu dan localStorage yang menyamarkan kegagalan database: INITIAL_MEMBERS sebagai pengganti data (member.service.ts), FALLBACK_LOGS (riwayat-piket), penyimpanan swap/override/tugas di localStorage (swap.service.ts, TodayDutyCard). Gantikan dengan state loading, empty, dan error yang jelas plus tombol coba lagi. INITIAL_MEMBERS boleh tetap hanya sebagai seed/dokumentasi, tidak dipakai saat runtime. Hapus juga indikator "Mode Lokal" di TopBar jika sudah tidak relevan.5. START DATE HARDCODED. useSchedule(activeMembers, '2026-08-31') dipanggil dengan tanggal literal di beberapa halaman dan TopBar. Ambil start_date dari tabel settings lewat satu hook useSettings (dengan Realtime) dan pakai di semua tempat.6. BUG TANGGAL/ZONA WAKTU. Di useSchedule (tomorrow.toISOString().split('T')[0]) dan Edge Function auto-mark-missed, toISOString memakai UTC sehingga di WIB (UTC+7) tanggal bisa mundur sehari sebelum jam 07.00. Buat util formatLocalDate(date) berbasis date-fns format(date, 'yyyy-MM-dd') untuk klien, dan di Edge Function hitung tanggal dengan zona Asia/Jakarta. Cari semua pemakaian toISOString().split('T') dan perbaiki.7. EDGE FUNCTION auto-mark-missed SALAH LOGIKA. Fungsi ini menandai SEMUA anggota aktif 'terlewat' kemarin jika belum punya log, padahal tiap hari hanya satu orang yang bertugas dan ada hari libur. Perbaiki: hitung siapa yang seharusnya piket kemarin memakai algoritma rotasi yang sama dengan src/lib/algorithms/scheduleRotation.ts (hormati settings.start_date, hari_libur, dan schedule_overrides), lewati hari libur, lewati log berstatus izin/ditukar/selesai, dan hanya tandai petugas yang benar-benar terjadwal. Pindahkan logika rotasi yang dipakai bersama ke modul yang bisa dipakai kedua sisi atau duplikasi dengan test yang membuktikan hasilnya sama. Fungsi harus idempotent dan aman dijalankan ulang. Dokumentasikan cara menjadwalkan via pg_cron.8. SCHEMA TIDAK IDEMPOTENT. Di supabase/schema.sql, ALTER PUBLICATION ... ADD TABLE gagal jika tabel sudah ada di publikasi dan INSERT seed tanpa unique constraint bisa menggandakan data (tasks, kos_rules, settings). Bungkus dengan pengecekan pg_publication_tables dan tambahkan constraint/ON CONFLICT yang tepat. Rapikan jadi migrasi bernomor di supabase/migrations/ dan tulis README singkat urutan menjalankannya.9. PENGATURAN & PERBARUAN BOROS. Di halaman pengaturan (kini admin/pengaturan), update nama anggota, nama tugas, dan peraturan dipanggil di setiap ketikan (onChange langsung ke database). Ubah menjadi debounce atau simpan eksplisit dengan tombol Simpan, dan tampilkan error jika gagal. handleSaveSettings sekarang selalu menampilkan "berhasil" walau update gagal; perbaiki agar jujur menampilkan hasil.10.
